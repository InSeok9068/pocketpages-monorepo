- **이슈 1 — 빠르게 위로 되돌릴 때 반동:** 실제 챕터 삽입 시나리오를 포함해 보통·빠른 입력 22회에서 큰 역방향 프레임이나 복구 오판은 0회였다. 600px 입력을 20ms 간격으로 40회 보내는 한계 스트레스에서는 특정 EPUB/WebKit 조합에서 3회 중 2회, 한 프레임 486px 반동이 반복됐다. 일반 사용자 영향이 확인되지 않아 이 로직은 수정하지 않았다.

- Booklog E2E 전체 실행 결과는 232개 중 215 통과, 17 건너뜀, 실패 0이다. Booklog lint도 통과했다.

## 환경과 시나리오

- 실제 EPUB 파일을 리더에서 열고, 목차 이동·본문 스크롤·챕터 경계·저장·새로고침 복원을 실행했다. 저장 API만 Playwright 가짜 API로 처리했다.
- Chrome `156.0.8078.48`, Playwright WebKit `27.2`, 화면 `390×844`; 4권을 양 브라우저에서 테스트했다.
- 경계 테스트는 긴 본문 시작에서 아래로 스크롤해 앞 챕터가 정리되도록 한 뒤, 위로 되돌아오는 방식으로 진행했다. 재삽입된 챕터에서 `counter` 보정과 다음 프레임 스크롤 검사가 발생했는지 함께 확인했다.
- WebKit은 Windows에서 실행한 Playwright 브라우저다. iOS Safari 실기기의 관성·바운스·스크롤 합성 동작은 검증하지 못했다.

## 수정 전: 이슈 1 — 위쪽 경계에서 한 프레임 반동

### 보통·빠른 입력

| 입력 등급 | 아래로 | 위로 | 책·브라우저 조합 | 복구 판정 / 80px 초과 반동 |
|---|---|---|---:|---:|
| 보통 빠른 읽기 | `+300px ×20`, 80ms 간격 | `−300px ×25`, 80ms 간격 | 4권 × Chrome/WebKit = 8 | 0/8 |
| 빠른 트랙패드식 훑기 | `+400px ×30`, 50ms 간격 | `−400px ×32`, 50ms 간격 | 4권 × Chrome/WebKit = 8 | 0/8 |
| 반복 확인 | 위 두 입력을 문제 후보 책 WebKit에서 각 3회 반복 | 동일 | 6회 | 보통 0/3, 빠른 0/3 |

각 입력 묶음에서 실제 앞 챕터 재삽입은 2–4회 발생했다. 따라서 재삽입 경로가 실행되지 않은 테스트는 아니다. 계측 기준 80px 미만의 작은 움직임까지 없었다는 의미는 아니다. 각 실행에서 JavaScript 페이지 오류도 없었다.

### 한계 스트레스와 원인 단서

WebKit에서 `+600px ×40`과 `−600px ×40`을 각각 20ms 간격으로 보냈다. 방향당 24,000 CSS px를 0.8초에 이동하는 입력이다.

| EPUB | 반복 수 | 복구가 감지된 횟수 |
|---|---:|---:|
| 날씨의 아이 | 3 | 0 |
| 또다시 같은 꿈을 꾸었어 | 3 | 2 |
| 모두에게 사랑받을 필요는 없다 | 3 | 0 |
| 코스모스 | 3 | 0 |

재현된 두 번은 모두 `또다시 같은 꿈을 꾸었어`의 spine 5와 직전 이미지 spine 4 사이였다. `counter` 이벤트는 `before=1224`, `written=1710`, `next=1110`, `delta=486`으로 기록됐다. 앞 이미지 챕터 높이 486px이 보정값이었다. 같은 계측 프레임에서 보이는 본문 요소 7개의 위치가 각각 `−486px` 이동했다. 다음 프레임의 복구 쓰기는 `scrollTop 1110 → 1596`을 적용했고, 다른 앞 챕터도 연달아 붙어 최종 `held:false`가 기록됐다.

과거 스트레스 로그에서도 날씨의 아이의 `600px ×40` WebKit 입력 3회 중 1회, 모두에게 사랑받을 필요는 없다의 `5000px ×40` WebKit 입력 4회 중 2회가 재현됐다. 반면 새 테스트의 시작 spine과 경계를 바꾸자 재현 책은 달라졌다. 모든 EPUB에 공통으로 나타나는 오류는 아니었다.

### 사용자 영향 판단과 조치

한 프레임 486px 이동은 스트레스 상황에서 눈에 띄는 반동이다. 다만 600px 휠 이벤트를 초당 50회, 0.8초 동안 보내는 것은 약 28 화면 높이를 연속 이동하는 극단 입력이다. 보통·빠른 입력에서는 22회 모두 재현되지 않았고, 반복 사례도 문제 책의 WebKit 보통 0/3·빠른 0/3이었다. 이 조건을 일반 독서 중 자주 겪는 오류로 보기는 어렵다.

코드는 수정하지 않았다. `guardScrollWrite` 복구를 단순히 제거하면 챕터 하나의 높이만큼 위치가 남을 수 있고, 이번 로그만으로 복구식을 바꾸면 더 안전하다고 입증할 수 없다. 후속 수정이 필요하다면 빠른 연속 prepend 중 사용자의 반대 방향 이동량을 보존하면서 보정을 합치는 접근을 검토해야 한다. 이를 확정하려면 실제 iOS Safari 또는 현실적인 입력에서 재현이 먼저 필요하다.

## 수정 전: 이슈 2 — 저장 위치 복원 시 문단이 밀림

`모두에게 사랑받을 필요는 없다`의 `page-189.html` (spine 30), 70% 지점에서 `+220px ×6`을 100ms 간격으로 스크롤해 저장한 뒤 다시 열었다. 같은 문단 앵커가 `y=50.9px → y=244.9px`로 **194px 아래로** 이동했다. Chrome·WebKit 및 챕터 HTML 로딩 지연 0ms·900ms 조건에서 같은 값이 나왔다. spine 22에서는 +167px, spine 38에서는 −21px이었다.

원인은 저장 CFI를 고르는 분기였다. epub.js 시작 CFI가 화면 상단보다 64px 넘게 위에 있으면 화면에서 처음 보이는 텍스트 위치를 찾아 보정하는데, 기존 코드는 화면에 걸친 텍스트 노드 전체를 선택한 뒤 시작 offset 0을 CFI로 저장했다. 문단 첫 부분이 화면 밖이어도 문단의 첫 글자를 저장했고, 복원 시 그 시작 위치로 이동하면서 읽던 문단이 밀렸다.

## 적용한 수정

[booklog-reader.js](../pb_hooks/pages/assets/booklog-reader.js)의 오프스크린 CFI 보정에만 변경을 적용했다.

- 텍스트 노드 시작 대신 화면 상단에 실제로 보이는 첫 문자 위치를 찾는다.
- `caretRangeFromPoint` 또는 `caretPositionFromPoint`를 우선 사용하고, 지원되지 않거나 다른 노드를 반환하면 문자별 화면 사각형으로 찾는다.
- 찾은 문자 위치로 CFI를 만들며, 화면 안에 있는 기존 CFI와 일반 저장 경로는 그대로 둔다.
